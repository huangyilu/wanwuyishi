## 1. 使用的系统/方法

本项目采用 **npm** 作为包管理器，通过 `package.json` 声明依赖，使用 `package-lock.json`（lockfileVersion 3）锁定所有依赖及其子依赖的确切版本与完整性校验和（integrity），确保构建可重现。项目未使用 pnpm、yarn、Bun 等替代工具，也未配置 `.npmrc` 或私有 npm registry。

## 2. 关键文件

- `package.json`：声明项目元信息、脚本命令、运行时依赖与开发依赖。
- `package-lock.json`：npm v7+ 生成的完整依赖树锁文件，记录每个包的精确版本、resolved URL（指向 https://registry.npmjs.org/）、sha512 integrity 校验值。
- `.gitignore`：忽略 `node_modules/`，不提交本地安装产物。
- `vite.config.ts` / `tsconfig.json`：构建与类型检查配置，间接决定依赖解析行为（如 ESM 模块、TypeScript 编译目标）。

## 3. 架构与约定

### 依赖分类
- **运行时依赖（dependencies）**：React 18、react-router-dom、maplibre-gl、@supabase/supabase-js、@tanstack/react-query、zod、zustand、@dnd-kit/*、pmtiles、leaflet 类型定义等，均为前端应用运行所需。
- **开发依赖（devDependencies）**：Vite、TypeScript、vitest、tsx、@types/*、@vitejs/plugin-react、agentation 等，仅用于开发、测试与构建阶段。

### 版本策略
- 所有依赖均使用 **语义化版本范围（^X.Y.Z）**，允许小版本/补丁升级，便于安全更新同时保持 API 兼容。
- 实际安装到 `node_modules` 的版本由 `package-lock.json` 锁定，CI/生产环境通过读取该文件获得确定性安装结果。

### 构建流水线中的依赖使用
- `npm run build` 会先执行 `content:check`（内容校验与索引构建），再执行 `tsc -b` 类型检查，最后 `vite build` 打包。
- 脚本通过 `tsx` 直接运行 TypeScript 脚本（`scripts/*.ts`），无需预编译。
- 测试通过 `vitest run` 执行，位于 `domain/*` 下的 `.test.ts` 文件。

### 外部服务依赖
- Supabase 客户端通过环境变量注入（`.env.example` 提供模板），不在代码中硬编码密钥。
- Edge Function（`supabase/functions/chat-proxy/index.ts`）调用 DeepSeek 等大模型，属于运行时外部依赖，非 npm 包。

## 4. 约定与约束

- **不使用 vendoring**：`node_modules/` 被 `.gitignore` 排除，依赖以 lockfile 形式提交而非源码拷贝。
- **无私有仓库/镜像配置**：未发现 `.npmrc`、`pnpm-workspace.yaml`、`yarn.lock` 或自定义 registry 配置，默认使用 npm 官方源。
- **单仓单项目**：不存在 monorepo/workspace 结构，所有依赖集中在根级 `package.json`。
- **Node.js 版本要求**：由依赖生态决定（如 Vite 5.x、React 18），未在项目中显式声明 `.nvmrc` 或 engines 字段，但可通过 `package-lock.json` 中各包的 `engines` 约束推断。
- **脚本即入口**：所有依赖的使用入口集中在 `package.json` 的 `scripts` 字段中，统一通过 npm 命令触发，避免开发者直接使用底层 CLI 导致环境不一致。

## 5. 总结

该项目是一个典型的现代前端单仓项目，依赖管理遵循 npm 标准实践：`package.json` 声明版本范围 + `package-lock.json` 锁定精确版本 + CI 通过 lockfile 保证可重复安装。没有复杂的私有源、monorepo 或 vendoring 机制，适合中小型项目的依赖治理需求。
