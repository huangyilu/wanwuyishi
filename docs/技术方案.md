## 1. 目标、约束与技术原则

### 1.1 从产品方案继承的硬约束

| # | 约束 | 工程含义 |
| --- | --- | --- |
| C1 | 基础设施成本必须为 0 | 不引入任何按量计费服务；不自建服务器；不做需要密钥的第三方 API（地图、汇率均走免费无 key 方案） |
| C2 | 世界库是静态知识，行程是运行时数据 | 双数据源架构，必须在数据访问层抽象掉两者差异 |
| C3 | 世界库要能从 JSON 平滑迁到数据库 | JSON schema 从第一天就按关系表设计；读写收口在 Repository |
| C4 | PC 与移动是两个形态，不是响应式 | 视图层双实现、领域层单实现；移动端不下载 PC 专属代码 |
| C5 | 行中可能无网 | 静态内容随 PWA 预缓存；行程数据支持离线只读快照 |
| C6 | 同伴不一定注册 | 身份（member）与账号（auth user）解耦，投票/记账引用 member 而非 user |
| C7 | 不承诺实时性，承诺可追溯 | 易变字段强制携带 source + verifiedAt，过期在 UI 层可视化 |
| C8 | 分享页面必须匿名可访问且不泄露隐私 | 分享用"发布快照"，不是对生产数据开只读权限 |

### 1.2 技术原则

1. **领域逻辑纯函数化。** 结算、闭馆校验、日期重映射、送签国判断这些"万无一失"的承诺全部写成无副作用的纯函数，放在 `src/domain/`，不依赖 React、不依赖网络，100% 单测覆盖。产品的信誉压在这几个函数上。
2. **数据访问单一出口。** 视图层永远不 import supabase client，也不 fetch JSON，只调 Repository。这是 C3 迁移成本可控的唯一保证。
3. **服务端不可信输入零信任，客户端权限不做安全边界。** anon key 本就公开，所有权限判定落在 RLS 与 SECURITY DEFINER 函数上，前端的按钮禁用只是体验。
4. **能在构建期做的事不放到运行时。** 世界库索引、搜索索引、闭馆日展开、坐标校验都在 `npm run build` 前跑完。
5. **宁可少一个功能，不要一个不可靠的功能。** 离线写、实时同步这类高复杂度特性明确后置，不做半成品。

### 1.3 时间线现实检查

今天 2026-08-04，预计出发 9 月中下旬，**可用工程时间约 6 周**，且这 6 周同时要做内容（约 40 个 POI）。因此：

⚠️ **方案调整建议 1：签证模块必须从 P1 提到 M1 首批。**
产品方案 5.4 指出"递签发生在出发前 1–2 个月"——按今天算，递签窗口就是**现在**。签证行程单导出是全产品**最早被真实需要**的功能，却被排在 P1。建议 M1 交付一个最小可用版本：行程时间线（哪怕只有日期+城市+住宿三列）+ 送签国统计 + 打印式行程单导出。这一条链路不依赖导览卡、不依赖地图、不依赖协作，一两天可完成，且是本次行程唯一有"死线"的功能。

⚠️ **方案调整建议 2：M1 的 demo 范围建议收窄为"能出行程单的时间线"，把三栏工作台完整形态挪到 M2。**
理由同上：三栏工作台的价值在长时间做攻略时的效率，而现在时间不足以先建工具再用工具。先跑通数据链路，再补交互密度。

### 2.3 双轨数据架构

| | 世界库（知识） | 行程（决策） |
| --- | --- | --- |
| 事实源 | `content/**/*.json`（git） | Supabase Postgres |
| 写入方式 | AI 草稿 → 人工核对 → PR → CI 校验 → 合并 → 部署 | 应用内实时写 |
| 读取方式 | `fetch('/data/...')` + SW 缓存 | supabase-js + TanStack Query |
| 版本控制 | git 历史 | `updated_at` + 导出快照 |
| 变更频率 | 低（内容多年不变，volatile 字段季度级） | 高（行前每天改） |
| 迁移计划 | POI > 100 或第二编辑者 → 入库（见第 15 章） | 无需迁移 |

**跨轨引用规则：** 行程侧只存字符串引用 `poi_id = "poi-louvre"`，不存外键，也不存冗余快照（导出离线快照时才物化）。这样世界库改标题、改导览内容，所有行程自动跟随；世界库删 POI 时行程侧降级为"内容已下架"占位卡（前端处理，不阻塞渲染）。

### 3.2 关键选型论证

**托管：GitHub Pages（产品方案既定；本方案先前误改为 Cloudflare Pages，已回退）。**
先前论证称"GitHub Pages 不支持 SPA fallback、无法配 CSP"——**不准确，在此更正**：GitHub Pages 免费档对纯静态 SPA 完全够用。
- **SPA fallback**：经典做法是把 `index.html` 复制为 `404.html`，刷新/深链不再 404。本项目进一步采用 **HashRouter**，所有路由落在 `#` 之后，服务器永远只收到 `/`——连 404.html 都不需要，对 GitHub Pages 子路径与离线（`file://`）都零配置兼容。
- **CSP**：GitHub Pages 不提供自定义响应头，故 CSP 改在 `index.html` 里用 `<meta http-equiv="Content-Security-Policy">` 声明（与 `_headers` 等价；仅 `frame-ancestors` / `report-uri` 两条 meta 不支持，已评估对本项目无影响，见 6.6）。
- **子路径**：项目页部署在 `username.github.io/<repo>/` 下，Vite 设 `base: './'` 走相对路径即可。
- **额度**：1 GB 仓库 / 100 GB 月带宽软上限，本体量（dist < 1 MB + 世界库 JSON 数十 KB）绰绰有余。
Cloudflare Pages 保留为**备份部署目标**（同仓库可双挂），不默认启用。若日后要干净 URL（无 `#`），可切回 `createBrowserRouter` + `404.html` 回退并显式设 `basename`，改动很小。

**状态管理：TanStack Query + Zustand，不用 Redux。**
本项目 90% 的状态是"服务端数据的本地投影"（行程、条目、账本），这类状态用 Query 管理缓存/失效/重试是最省代码的；剩下 10% 是 UI 状态（当前选中日、右栏展开的实体、筛选条件），Zustand 一个 store 搞定。Redux Toolkit 在这个规模上是纯负担。

**拖拽：dnd-kit 而非 react-beautiful-dnd。**
后者已停止维护且不兼容 React 18 StrictMode 的双调用；dnd-kit 支持多容器排序（跨天拖拽正是这个场景）、键盘可达（对应产品方案"键盘友好"要求）、无需包装 DOM 结构。

**地图：Leaflet 而非 MapLibre GL。**
MapLibre 需要矢量瓦片源，免费无 key 的矢量源（如 Protomaps）要自己托管 pmtiles（数百 MB，超出 Pages 单文件限制）。Leaflet + OSM 光栅瓦片是唯一真正零成本零配置的组合。
⚠️ **合规提醒**：OSM 官方瓦片有 [Tile Usage Policy](https://operations.osmfoundation.org/policies/tiles/)，禁止大流量与批量下载。个人项目在线浏览属允许范围，但**离线地图必须放弃**（批量缓存瓦片违反政策）。行中离线只提供 POI 列表与坐标，地图降级为"无网时显示静态占位 + 一键跳转系统地图 App"。

**校验：zod 作为唯一 schema 源。**
世界库 JSON 的类型、CI 校验、前端运行时容错三处需求用一个 zod schema 同时满足（`z.infer` 出类型，`safeParse` 做校验）。备选 JSON Schema + ajv 需要额外维护类型定义，淘汰。

**PDF 导出：浏览器打印（`window.print()` + `@media print` 样式），不引入 jsPDF/pdfmake。**
中文 PDF 生成需要嵌入中文字体（最小子集也有数 MB），会拖垮首屏预算；而签证行程单与旅行记录的 PDF 需求都是"打印/另存为 PDF"，浏览器原生能力质量更好、字体零成本。

**不选用的东西（显式记录）：**
Next.js（需要 SSR 运行时，与静态托管的零成本前提冲突）、Tailwind（团队只有一人，CSS Modules + token 已足够，且避免类名污染 HTML 可读性）、Redux、Firebase（免费档需绑卡）、任何汇率 API（改为手填汇率 + 预置常用汇率常量，见 8.2）。

## 4. 数据模型

### 4.1 世界库 schema

产品方案 4.3 给出的结构基本可用，但**缺少支撑核心算法的结构化字段**。以下是补齐后的完整定义（zod 版见 `src/domain/world/schema.ts`）：

```ts
// ---------- 公共 ----------
type Verifiable<T> = {
  value: T;
  source: string;        // 官方源 URL，必填
  verifiedAt: string;    // YYYY-MM-DD，必填
};

// ---------- Country ----------
interface Country {
  id: string;                    // "fr" (ISO 3166-1 alpha-2)
  name: string;                  // 法国
  localName: string;             // France
  currency: string;              // "EUR"
  languages: string[];
  timezone: string;              // "Europe/Paris"
  plugTypes: string[];           // ["C","E"]
  emergencyNumbers: Record<string, string>;
  visa?: VisaInfo;
  tipping?: string;
}

interface VisaInfo {
  visaArea?: string;             // "schengen" —— 同区多国共享卡片
  type: string;                  // 短期旅游签（C类）
  applyChannel: string;
  materials: string[];
  fee: Verifiable<string>;
  processingDays: Verifiable<string>;
  earliestApplyDays: number;     // 最早可递签：出发前 N 天
  latestApplyDays: number;       // 建议最晚：出发前 N 天（用于倒计时告警）
  notes?: string[];
}

// ---------- City ----------
interface City {
  id: string;                    // "city-paris"
  name: string; localName: string;
  country: string;               // "fr"
  location: { lat: number; lng: number };
  timezone: string;
  survival: SurvivalTopic[];
  transitPasses?: TransitPass[]; // 城市通票（P1 交通模块）
}

interface SurvivalTopic {
  topic: 'toilet' | 'wifi' | 'water' | 'tipping' | 'safety' | 'transport' | 'payment' | 'other';
  summary: string;
  tips: string[];
  source: string;
  verifiedAt: string;
}

// ---------- POI ----------
interface Poi {
  id: string;                    // "poi-louvre"
  type: 'museum' | 'landmark' | 'park' | 'viewpoint' | 'church' | 'market'
      | 'restaurant' | 'station' | 'facility' | 'other';
  name: string;                  // 卢浮宫
  localName: string;             // Musée du Louvre
  city: string;                  // "city-paris"
  country: string;               // "fr"
  location: { lat: number; lng: number };
  tags: string[];
  popularity: number;            // 0-100，城市页排序

  // ↓↓↓ 相对产品方案新增，均为算法必需 ↓↓↓
  wikidataId?: string;           // "Q19675"，骨架来源与去重键
  officialUrl?: string;
  visit: {
    durationMinutes: [number, number];   // [180, 240] 结构化，供"一天排太满"体检
    durationNote?: string;               // "3-4小时（精华）/ 半天+（细逛）" 展示用
    bestTime?: string;
  };
  openness: {
    closedWeekdays: number[];    // [2] = 周二闭馆（0=周日 … 6=周六）
    closedDates?: string[];      // ["2026-12-25","2026-05-01"] 固定闭馆日
    seasonal?: { from: string; to: string; note: string }[]; // MM-DD 区间
  };
  booking?: {
    required: boolean;
    leadDays: number;            // 建议提前 N 天预约 → 驱动"该订票了"提醒
    url?: string;
  };
  facilities?: {
    toilet?: string; wifi?: string; locker?: string;
    accessible?: boolean; water?: string;
  };
  volatile: {
    price?: Verifiable<string>;
    hours?: Verifiable<string>;
    booking?: Verifiable<string>;
  };
  guide?: Guide;                 // 可选扩展，博物馆默认配备
  image?: { url: string; credit: string; license: string }; // Wikimedia Commons，须署名
}

interface Guide {
  entrances?: string;
  routes: { name: string; durationMinutes?: number; stops: string[] }[];
  highlights: { name: string; location: string; why?: string }[];
  collections?: string;
  tips: string[];
}
```

**相对产品方案的四处关键增补及理由：**

| 增补字段 | 为什么必须现在加 |
| --- | --- |
| `openness.closedWeekdays / closedDates / seasonal` | 5.2「无脑跟随的闭馆日校验」是产品的招牌细节，没有这个字段就无法实现。且它必须是结构化数组，不能藏在 `volatile.hours` 的自然语言里 |
| `visit.durationMinutes` 数字区间 | 「一天排太满」体检、路线时长估算都需要可运算的数值；原方案只有 "3-4小时" 文本 |
| `booking.leadDays` | 产品方案 P0 门票管理明确要求"需提前 N 天预约提醒"，字段必须落在 POI（知识）而非 ticket（决策）上，这样任何行程引用它都自动获得提醒 |
| `wikidataId` | 内容供应链用 Wikidata 铺骨架，需要稳定去重键；也是未来入库时的自然主键候选 |

⚠️ **方案调整建议 3：`facilities` 与 `survival` 的关系需要明确为"POI 覆盖城市默认"。**
产品方案里两者并列存在但没说优先级。技术上定为：渲染 POI 详情时，`poi.facilities.toilet` 存在则显示它，否则回落到所在城市 `survival` 中 topic=toilet 的 summary，并标注"（本市通用）"。这个回落规则写在 `domain/world/resolve-facility.ts`。

### 4.2 ID 与命名规范

| 实体 | ID 形式 | 例 | 备注 |
| --- | --- | --- | --- |
| Country | ISO alpha-2 小写 | `fr` | 直接作文件名 `content/countries/fr.json` |
| City | `city-<slug>` | `city-paris` | slug 用英文小写，不用拼音 |
| POI | `poi-<slug>` | `poi-louvre` | 一旦发布不得修改（行程数据里存的是它） |
| 行程侧实体 | uuid v4 | — | 数据库生成 |

**ID 稳定性是硬规矩**：POI id 改名等于让所有引用它的行程指向空。若必须重命名，加 `aliases: ["poi-old-id"]` 字段并在 Repository 层做重定向。

### 4.3 金额、货币与时间规范

- **金额一律用整数分存储**（`amount_cents bigint`），前端展示时除以 100。浮点数做 AA 分摊必然出现 0.01 误差累积，而账本算错就是"扯皮"，与产品目标直接冲突。
- **多币种**：每笔支出记 `currency` 原币种 + `fx_rate`（换算到 `trip.base_currency`）。汇率**手填**，App 内置一张常用汇率常量表作为默认值（EUR/CHF/CNY），出发前手动更新一次。理由：任何免费汇率 API 都需要注册 key，违反 C1；而旅行结算精度到「大致」即可。
- **时间**：日期用 `date`（无时区），时刻用 `time`，仅审计字段用 `timestamptz`。行程日期绝不能受时区影响——用户在国内规划欧洲行程时，`new Date('2026-09-20')` 的时区陷阱是此类应用最常见 bug。domain 层统一用 `YYYY-MM-DD` 字符串做日期运算，禁止把行程日期塞进 `Date` 对象。

### 4.4 Supabase 表结构

共 13 张表。完整 DDL 见 `supabase/migrations/0001_init.sql`，此处给出关系与设计要点。

```
profiles (= auth.users 的公开扩展)
   │
   └─< trips ──< trip_members  (user_id 可为 NULL = 幽灵成员)
         │            ▲  ▲  ▲
         ├─< trip_days ─┼──┼──┼─────────────┐
         │     └─< trip_items ─< item_votes │
         │              │                    │
         ├─< tickets ───┘                    │
         ├─< expenses ──< expense_shares ────┘
         ├─< transports
         ├─< accommodations
         ├─< personal_notes  (仅本人可读)
         ├─< trip_invites
         └─< shares          (发布快照，匿名经 RPC 只读)
```

设计要点：

1. **所有子表冗余 `trip_id`。** `item_votes`、`expense_shares` 理论上可以经 join 推出 trip_id，但 RLS 策略里做 join 既慢又容易写出递归。冗余一列换来所有策略统一为 `is_trip_member(trip_id)`，这是本设计里性价比最高的一处妥协。
2. **`trip_members` 是投票与账本的唯一主体。** `item_votes.member_id`、`expenses.payer_member_id` 都引用 member 而非 user。这直接兑现 C6：幽灵成员天然可被投票、可被记账、可被结算。
3. **真人退化为幽灵而非消失。** `trip_members.user_id` 的外键是 `ON DELETE SET NULL`：某人注销账号，他在行程里的身份变成一个只有名字的幽灵成员，历史账本与投票全部保留、不产生悬空引用。
4. **`trip_members.display_name` 冗余存名字**（不从 profiles 关联读）。副作用是改名不同步，收益是 **profiles 表可以完全不对他人开放读权限**——同伴列表渲染不需要跨用户读 profiles，隐私边界更干净。收益大于副作用。
5. **`trip_items.day_id` 可为 NULL**，表示"候选池"（已加入行程但未排期）。产品方案的三态状态机在实际使用中一定会出现"想去但还没决定哪天"，候选池是必要的暂存区。
6. **`trip_items.rank` 是字符串**，用 fractional indexing 排序（见 8.1），不用整数 order——拖拽一次只改一行，避免整天条目重排。
7. **`shares.payload` 存已净化的 JSON 快照**，不是对生产表开只读权限。理由见 6.5。

### 5.3 查询与缓存策略

**TripBundle 一次性加载。** 行程页需要 days + items + votes + tickets + expenses + members，逐个请求会产生 6 次往返。改为一次 RPC `get_trip_bundle(trip_id)` 返回单个 JSON，前端在内存里切分。理由：Supabase 免费档没有连接池优势，往返延迟（国内访问 Supabase 新加坡/东京节点约 100–200ms）是主要瓶颈。

Query Key 约定：

```
['world','pois', cityId, filterHash]   staleTime: Infinity   (静态内容，版本变更由 SW 处理)
['world','poi', poiId]                 staleTime: Infinity
['trip','bundle', tripId]              staleTime: 30_000
['trip','list']                        staleTime: 60_000
```

**写操作一律乐观更新**：`onMutate` 直接改 `['trip','bundle']` 缓存，失败回滚并 toast。拖拽排程如果等网络往返会明显卡顿，这是 PC 端"趁手"体验的关键。

### 5.4 并发与冲突

MVP 不做 CRDT/OT，采用**字段级最后写入胜出 + 实体级版本提示**：

- 每张表有 `updated_at`；更新时带上读到的 `updated_at` 做 `WHERE updated_at = $expected`，影响行数为 0 说明被他人改过 → 前端提示"该条目刚被 XX 修改，已刷新"，并重载 bundle。
- 拖拽排序天然抗冲突：fractional index 让两人同时插入同一位置也只是产生相邻的两个 rank，不会互相覆盖。
- P3 实时同步接入 Supabase Realtime 时，只需在 bundle query 上加 `postgres_changes` 订阅触发 invalidate，架构无需改动。

## 6. 认证、权限与安全

### 6.1 Auth 配置

- 方式：邮箱 + 密码；Supabase 后台**关闭 Confirm email**（注册即用，符合产品方案"注册门槛绝不挡在工具使用前面"）。
- 邮箱唯一用途：忘记密码重置链接。免费档内置邮件有每小时配额限制，个人使用足够。
- 会话：`persistSession: true` + `autoRefreshToken: true`（localStorage）。**微信内置浏览器场景**：iOS 微信 WKWebView 会保留 localStorage，refresh token 静默续期可用；但需处理 `visibilitychange` 时主动 `getSession()` 一次，避免长时间后台后首个请求 401。
- **登录态闪烁**：`AuthProvider` 初始 `status: 'loading'`，路由守卫在 loading 时渲染骨架屏，禁止在 loading 阶段重定向到登录页。这是产品方案明确点名的体验要求。

### 6.2 三种角色的技术映射

| 产品角色 | 技术实现 |
| --- | --- |
| owner | `trips.owner_id = auth.uid()`，同时在 trip_members 中 role='owner' |
| member | `trip_members` 中存在 `user_id = auth.uid()` 的行 |
| 幽灵成员 | `trip_members` 中 `user_id IS NULL` 的行，**无任何权限，只是被引用的名字** |
| visitor | 未登录 / 非成员，只能经 `get_share(slug)` RPC 读快照 |

### 6.3 RLS 策略

**防递归的关键**：`trip_members` 表自身的 SELECT 策略若写成"能读自己所在行程的成员"，会在判断时再次查 trip_members 触发递归。解决方案是 `SECURITY DEFINER` 函数（绕过 RLS 执行内部查询）：

```sql
create or replace function public.is_trip_member(p_trip_id uuid)
returns boolean
language sql
security definer
stable
set search_path = public
as $$
  select exists (
    select 1 from public.trip_members m
    where m.trip_id = p_trip_id and m.user_id = auth.uid()
  );
$$;

create or replace function public.is_trip_owner(p_trip_id uuid)
returns boolean language sql security definer stable set search_path = public as $$
  select exists (select 1 from public.trips t
                 where t.id = p_trip_id and t.owner_id = auth.uid());
$$;
```

策略模板（所有行程子表统一）：

```sql
alter table public.trip_items enable row level security;

create policy "member_read"  on public.trip_items
  for select using (public.is_trip_member(trip_id));

create policy "member_write" on public.trip_items
  for all using (public.is_trip_member(trip_id))
       with check (public.is_trip_member(trip_id));
```

特例：

| 表 | 特殊策略 |
| --- | --- |
| `profiles` | 仅本人可读写（`id = auth.uid()`）。他人展示名走 `trip_members.display_name` |
| `trips` | SELECT: `is_trip_member(id)`；INSERT: `owner_id = auth.uid()`；DELETE: 仅 owner |
| `trip_members` | SELECT: 成员可读；INSERT/UPDATE/DELETE: 仅 owner（加入房间走 RPC） |
| `personal_notes` | 全部操作限 `user_id = auth.uid()`，成员之间也互不可见 |
| `trip_invites` | 成员可读（拿邀请链接）；匿名不可读；使用走 RPC |
| `shares` | **不开放任何直接访问**，见 6.5 |

**鸡生蛋问题**：创建 trip 后 owner 还不是 member，无法读自己刚建的行程。用触发器解决：

```sql
create or replace function public.on_trip_created() returns trigger
language plpgsql security definer set search_path = public as $$
begin
  insert into public.trip_members (trip_id, user_id, display_name, role)
  select new.id, new.owner_id, coalesce(p.display_name, '我'), 'owner'
  from public.profiles p where p.id = new.owner_id;
  return new;
end $$;

create trigger trg_trip_created after insert on public.trips
  for each row execute function public.on_trip_created();
```

### 6.4 邀请与加入（RPC）

不能给 authenticated 用户开 `trip_members` 的 INSERT 权限（否则任何人可把自己塞进任何房间）。加入必须经过 SECURITY DEFINER 函数校验 token：

```sql
create or replace function public.join_trip_by_token(p_token text, p_display_name text default null)
returns uuid
language plpgsql security definer set search_path = public as $$
declare v_invite public.trip_invites; v_member_id uuid;
begin
  select * into v_invite from public.trip_invites
   where token = p_token
     and (expires_at is null or expires_at > now())
     and used_count < max_uses;
  if not found then raise exception 'INVALID_INVITE'; end if;

  -- 已是成员则幂等返回
  select id into v_member_id from public.trip_members
   where trip_id = v_invite.trip_id and user_id = auth.uid();
  if found then return v_member_id; end if;

  if v_invite.claim_member_id is not null then
    -- 定向邀请：认领一个幽灵成员，继承其全部投票与账本记录
    update public.trip_members
       set user_id = auth.uid(),
           display_name = coalesce(p_display_name, display_name)
     where id = v_invite.claim_member_id and user_id is null
    returning id into v_member_id;
  end if;

  if v_member_id is null then
    insert into public.trip_members (trip_id, user_id, display_name, role)
    values (v_invite.trip_id, auth.uid(), coalesce(p_display_name,'旅伴'), 'member')
    returning id into v_member_id;
  end if;

  update public.trip_invites set used_count = used_count + 1 where id = v_invite.id;
  return v_member_id;
end $$;

revoke all on function public.join_trip_by_token from public;
grant execute on function public.join_trip_by_token to authenticated;
```

**幽灵成员认领**是这里的亮点：先建幽灵成员照常记账投票，某天他想参与协作了，发一个 `claim_member_id` 定向邀请，他注册后直接继承此前所有历史，无需数据迁移。

### 6.5 分享：发布快照模型

产品方案 5.3 要求分享带隐私净化。有两种实现：

| 方案 | 问题 |
| --- | --- |
| A. 匿名只读访问生产表 + 视图过滤 | 净化逻辑写在 SQL 视图里，任何一处策略疏漏就是隐私泄漏；且行程后续修改会实时反映到已分享链接，作者失去控制 |
| B. **发布时生成净化快照存 `shares.payload`** ✅ | 净化是一次性的纯函数（可单测），生产表对匿名完全关闭；已发布内容不会因后续编辑意外变化；重新发布 = 覆盖快照 |

采用 B。安全细节：

```sql
-- shares 表不开放任何 policy（RLS 开启 + 零策略 = 匿名与登录用户都读不到）
alter table public.shares enable row level security;
create policy "owner_manage" on public.shares
  for all using (public.is_trip_owner(trip_id)) with check (public.is_trip_owner(trip_id));

-- 匿名访问唯一入口：按 slug 精确取，不可枚举
create or replace function public.get_share(p_slug text)
returns jsonb language sql security definer stable set search_path = public as $$
  select s.payload from public.shares s
   where s.slug = p_slug and s.revoked_at is null;
$$;
grant execute on function public.get_share to anon, authenticated;
```

⚠️ 若图省事给 shares 表加一条 `for select using (revoked_at is null)` 的匿名策略，攻击者可以直接 `GET /rest/v1/shares?select=*` **拉走全部分享内容**——PostgREST 会老实返回整表。RPC 精确查询是必须的。

slug 生成：`crypto.getRandomValues` → base62 22 位（约 130 bit 熵），不可枚举。

### 6.6 安全清单

- [x] anon key 公开无风险，全部权限落 RLS；service_role key **永不进前端仓库**（本项目根本不需要它）
- [x] 所有 SECURITY DEFINER 函数显式 `set search_path = public`，防 search_path 注入
- [x] 用户输入的笔记以 Markdown 渲染 → `marked` 输出经 `DOMPurify.sanitize` 后插入
- [x] `index.html` 内 `<meta http-equiv="Content-Security-Policy">` 声明 CSP：`default-src 'self'; connect-src 'self' https://*.supabase.co; img-src 'self' data: https://*.tile.openstreetmap.org https://upload.wikimedia.org https://*.wikimedia.org; script-src 'self'; style-src 'self' 'unsafe-inline'; base-uri 'self'; form-action 'self'`（GitHub Pages 无自定义响应头，故走 meta；`frame-ancestors`/`report-uri` meta 不支持，本项目无影响）
- [x] volatile 字段的 `source` 外链一律 `target="_blank" rel="noopener noreferrer"`（同时满足 5.5「多窗口核对」）
- [x] **明确禁止存储证件信息**：护照号、身份证号、出生日期不进任何表。签证行程单导出只含行程与住宿，个人信息由用户在打印件上手写或另行填写
- [x] 票券 `booking_ref` 属半敏感，分享快照生成时无条件剔除（净化函数单测覆盖此项）

### 7.2 双端分流机制

不是响应式，也不是两个应用，而是**单应用 + 布局分流**：

```tsx
// src/app/AppShell.tsx
const DesktopApp = lazy(() => import('../layouts/desktop/DesktopApp'));
const MobileApp  = lazy(() => import('../layouts/mobile/MobileApp'));

export function AppShell() {
  const mode = useViewMode();            // 'desktop' | 'mobile'
  return (
    <Suspense fallback={<AppSkeleton />}>
      {mode === 'desktop' ? <DesktopApp /> : <MobileApp />}
    </Suspense>
  );
}
```

- 判定：`matchMedia('(min-width: 1024px) and (pointer: fine)')`，另存用户手动覆盖（localStorage），PC 上可强制预览移动端。
- **代码分割收益**：dnd-kit、Leaflet 编辑态、记录编辑器只在 desktop chunk 里，移动端首包不下载。移动端首屏 JS 预算 **< 120KB gzip**。
- 共享的是 `features/*` 的 hooks（数据与业务）与 `domain/*`；两端各写各的 JSX，绝不做 `isMobile ? A : B` 的条件渲染混排——那正是"响应式凑合"的开始。

## 8. 核心算法

以下全部位于 `src/domain/`，纯函数、无副作用、100% 单测覆盖。

### 8.1 拖拽排序：fractional indexing

```ts
// domain/trip/rank.ts
// 在 a 与 b 之间生成一个字典序介于两者的字符串；a/b 可为 null（表示头/尾）
export function rankBetween(a: string | null, b: string | null): string
```

实现用 base62 中点法（参考 Figma/Notion 的 LexoRank 思路）。收益：跨天拖动只 UPDATE 一行，且两人同时插入同一位置不会互相覆盖（对应 5.4）。
边界：连续在同一位置插入会让 rank 字符串变长，超过 32 字符时触发该天的一次性重排（`rebalanceDay`），实际使用几乎不会触发。

### 8.2 AA 账本：分摊与最少转账结算

**第一步：分摊到人（整数分，无误差）**

```ts
// domain/expense/split.ts
// 按权重把 amountCents 分给 members，保证 sum(result) === amountCents
export function splitCents(amountCents: number, weights: number[]): number[] {
  const total = weights.reduce((a, b) => a + b, 0);
  const raw = weights.map(w => (amountCents * w) / total);
  const floors = raw.map(Math.floor);
  let remainder = amountCents - floors.reduce((a, b) => a + b, 0);
  // 余数按小数部分从大到小分配，保证总额精确且分配公平
  const order = raw.map((v, i) => [v - floors[i], i] as const)
                   .sort((x, y) => y[0] - x[0]);
  for (const [, i] of order) { if (remainder-- <= 0) break; floors[i] += 1; }
  return floors;
}
```

**第二步：净额计算**
`net[member] = Σ(他垫付的) − Σ(他应摊的)`，全部换算到 `trip.base_currency`（`amount_cents * fx_rate` 后四舍五入到分）。校验不变式：`Σ net === 0`，不成立直接抛错（说明数据有问题，宁可报错也不能算错）。

**第三步：最少转账次数**

```ts
// domain/expense/settle.ts
export function settle(nets: Map<MemberId, number>): Transfer[]
```

- 成员数 n ≤ 8（旅行团规模现实上限）：用**回溯 + 剪枝**求真正的最小转账次数，复杂度可接受（毫秒级）。
- n > 8：退化为**贪心**（最大债权人 ↔ 最大债务人配对，最多 n−1 笔），保证不超过 n−1 笔。
- 输出 `{from, to, cents}[]`，并附带一行人话解释："3 人共 4 笔支出，2 次转账即可结清"。

⚠️ 已知取舍：最小转账次数问题（等价于子集和划分）是 NP-hard，因此按人数分流处理。这个取舍要写在代码注释里，避免未来误以为是 bug。

### 8.3 日期重映射 + 闭馆日校验（无脑跟随核心）

```ts
// domain/trip/date-remap.ts
export function remapDates(sourceDays: SourceDay[], newStart: string): RemappedDay[]
// 纯字符串日期运算（见 4.3），偏移 = newStart − sourceDays[0].date

// domain/trip/closure-check.ts
export interface ClosureConflict {
  itemId: string; poiId: string; poiName: string;
  date: string; weekday: number;
  reason: 'weekday' | 'fixedDate' | 'seasonal';
  suggestion?: { swapWithDate: string; note: string };
}
export function checkClosures(days: RemappedDay[], pois: Record<string, Poi>): ClosureConflict[]
```

判定顺序：`closedDates` 命中 → `closedWeekdays` 命中 → `seasonal` 区间外命中。

**换日建议算法**（这是"万无一失"的具体兑现）：
对每个冲突条目，遍历同城的其他日期 d，若满足 ① 该 POI 在 d 开放；② d 当天没有已确认票券锁死时段；③ 与 d 交换的条目在原日期也开放 —— 则给出建议"把卢浮宫和 9/22 的奥赛博物馆对调"。找不到则提示"该日闭馆，建议移出行程或延长停留"。

同一套算法在三处复用：无脑跟随导入时、用户手动拖拽后即时校验、行前核验清单。

### 8.4 行程合理性体检

```ts
// domain/trip/sanity-check.ts
export type Issue =
  | { level: 'error';   code: 'CLOSED'          ; ... }   // 闭馆日
  | { level: 'error';   code: 'TICKET_DEADLINE' ; ... }   // 距出发 < leadDays 且未订票
  | { level: 'warn';    code: 'OVERPACKED'      ; ... }   // 当日 Σduration + 交通 > 10h
  | { level: 'warn';    code: 'BACKTRACK'       ; ... }   // 日内路径存在明显折返
  | { level: 'warn';    code: 'STALE_INFO'      ; ... }   // 引用 POI 的 volatile > 90 天未核实
  | { level: 'info';    code: 'NO_LUNCH_GAP'    ; ... };  // 11:00-14:00 无空档
```

- 距离与耗时估算：Haversine 直线距离 × 1.35（城市路网系数），步行 4.5km/h，>2.5km 按公交 18km/h + 10 分钟等候。**不调任何路径规划 API**（要 key，违反 C1），精度足够做"体检"而非导航。
- 折返判定：日内路径总长 / 首尾直线距离 > 2.5 且总长 > 6km。
- 体检结果在 PC 中栏顶部以一行摘要呈现（"2 个问题待处理"），点开是清单，每条可一键定位到条目。

### 8.5 送签国判断

```ts
// domain/visa/destination-country.ts
export function decideVisaCountry(days: TripDay[], cities: Record<string, City>): {
  country: string; nights: Record<string, number>; rule: 'most-nights' | 'first-entry'; reason: string;
}
```

规则：按天统计各国**过夜数**（第 i 天的过夜国 = 第 i 天所在城市的国家，最后一天不计过夜）；取最多者；并列时取首个入境国（第 1 天所在国）。输出附带明细表与人话理由，例如："法国 5 晚、意大利 4 晚、瑞士 2 晚 → 应向法国递签"。

同签证区判定：`country.visa.visaArea` 相同的国家共享一张签证卡，行程页只显示一张"申根签"卡片 + 送签国结论。

### 8.6 时效性

```ts
// domain/world/staleness.ts
export function staleness(verifiedAt: string, today = todayStr()) {
  const days = diffDays(today, verifiedAt);
  return { days, level: days > 180 ? 'expired' : days > 90 ? 'stale' : 'fresh' };
}
```

UI 规则：`fresh` 显示"核实于 2026-08-04"；`stale` 加橙色"信息可能已过期"；`expired` 加红色且把"查看官方最新"按钮提到值旁边。三种状态下 source 链接始终可见——这是 C7 的落点。

### 8.7 无脑跟随管线

```
读取分享快照 payload
  → 提取 days[].items[].poiId + slot + 天结构           (不含票券/账本/个人笔记)
  → 用户选择出发日期
  → remapDates()
  → checkClosures() → 展示冲突与换日建议（可一键应用）
  → createTrip({ sourceTripId })  + 批量 insert days/items
  → 全部 status 重置为 'candidate'
  → 跳转新行程工作台
```

批量插入用一个 RPC `clone_trip_from_share(slug, start_date, title)` 在服务端事务内完成，避免 N 次往返与半途失败留下残缺行程。来源归属通过 `trips.source_trip_id` 记录，行程页顶部展示"跟随自《XX 的法意瑞 12 天》"。

### 8.8 旅行记录编译与隐私净化

```ts
// domain/record/compile.ts
compile(bundle, world, options): RecordDoc      // 结构化中间表示（AST）
// domain/record/privacy-filter.ts
sanitize(bundle, scope): SanitizedBundle        // 发布前净化，纯函数，单测重点
```

**两段式设计**：先净化再编译，保证"被净化掉的数据从未进入渲染管线"，而不是渲染后再遮蔽。

净化规则（对应产品方案 5.3 第二层）：

| 数据 | 规则 |
| --- | --- |
| `tickets.booking_ref` | **无条件删除**（不受任何开关影响） |
| tickets 其余 | scope.tickets 开启时保留 channel / price / timeSlot / officialUrl |
| expenses | 默认聚合为：人均总额、分类小计、日均；`scope.expenseDetail` 才输出流水；payer 按开关化名为"旅伴 A/B" |
| accommodations | `scope.hideHotelName` 时只保留城市 + 区域 + 价位段（`€150-200`） |
| personal_notes | **永不进入快照**（连查询都不查） |
| item.note（共享笔记） | 受 `scope.notes` 控制 |
| members | 只输出 display_name，不输出 user_id |

渲染目标由同一个 `RecordDoc` 派生：
- **Markdown**：字符串拼接，用于粘贴到任意平台。
- **单文件 HTML**：内联 CSS + 内联数据，双击即可打开，是最好的离线备份格式。
- **PDF**：打开 HTML 后 `window.print()`，`@media print` 控制分页（每天一页起）。

### 8.9 签证行程单导出

递签所需的行程单是一张严格表格：`日期 | 城市 | 交通方式 | 住宿名称与地址`。

## 10. PWA 与离线

### 10.1 缓存策略

`vite-plugin-pwa`（Workbox generateSW）分资源类型配置：

| 资源 | 策略 | 说明 |
| --- | --- | --- |

### 11.2 Wikidata 骨架脚本

```sparql
# 巴黎的博物馆
SELECT ?item ?itemLabel ?localLabel ?coord ?website ?article WHERE {
  ?item wdt:P31/wdt:P279* wd:Q33506 ;      # instance of / subclass of museum
        wdt:P131* wd:Q90 .                  # located in Paris
  OPTIONAL { ?item wdt:P625 ?coord }        # coordinates
  OPTIONAL { ?item wdt:P856 ?website }      # official website
  OPTIONAL { ?article schema:about ?item ; schema:isPartOf <https://zh.wikipedia.org/> }
  SERVICE wikibase:label { bd:serviceParam wikibase:language "zh,fr,en". }
}
```

脚本要点：遵守 WDQS 限流（串行 + 1s 间隔 + User-Agent 标注用途）；已存在 `wikidataId` 的 POI 只补空字段不覆盖人工内容（幂等）；输出到 `content/pois/` 待人工筛选，**不自动进主分支**。

Wikipedia 摘要仅作参考写入注释，不直接进 `guide`（CC BY-SA 需署名，且质量不稳）。图片走 Wikimedia Commons 并强制填 `image.credit` + `license`。

### 11.3 CI 校验门禁

`scripts/validate-content.ts` 除 zod 结构校验外，还检查业务规则：

1. 所有 `city` / `country` 引用存在（引用完整性）
2. 坐标在国家边界框内（低成本查错，防经纬度写反）
3. `volatile.*` 必须同时有 `source`（https 开头）与 `verifiedAt`（合法日期，不晚于今天）
4. `type === 'museum'` 且 `popularity >= 80` 时**必须有 `guide`**（保证重点馆不漏导览）
5. `guide.highlights[].location` 非空（"亮点在哪个展厅"是深导览的核心价值）
6. POI id 唯一、不含大写与空格；文件名与 id 一致
7. 任意 `verifiedAt` 超过 180 天 → 警告（不阻断）

CI 失败即 PR 不可合并。这套门禁是"内容质量"唯一可自动化的部分，值得先写。

### 11.4 索引构建

`build-index.ts` 产出三类文件：

| 产物 | 内容 | 大小估计 |
| --- | --- | --- |
| `/data/index.json` | 全部 POI 精简字段（id/name/localName/city/type/tags/popularity/coord/closedWeekdays） | 40 POI ≈ 20KB |
| `/data/search.json` | MiniSearch 预建索引（中文分词用 bigram） | ≈ 30KB |
| `/data/pois/{id}.json` | 完整 POI（含 guide） | 每个 3–8KB，按需加载 |

首屏只加载 index.json，城市页与地图直接可用；进入某个 POI 才拉详情。规模到 500 POI 时 index.json 约 250KB，届时改为按城市分片（`/data/index/city-paris.json`），接口不变。

### 11.5 AI 草稿 prompt 契约

`content/README.md` 中固定一份 prompt 模板，要求 AI：

- 严格输出符合 schema 的 JSON，**不允许编造 source URL**；不确定的 volatile 字段填 `null` 并在 `_todo` 数组里列出需人工核实项。
- `guide.highlights[].location` 必须精确到展厅/馆翼；无法确定则不写该亮点。
- `openness.closedWeekdays` 用数字数组，不许写"周二闭馆"文本。
- 输出附 `_sources` 数组列出参考来源，供人工核对时按图索骥。

`_todo` / `_sources` 是下划线前缀的**编著期字段**，`build-index.ts` 在产出 public 数据时剥离，不进运行时。

## 12. 构建、部署与环境

### 12.1 环境变量

```
VITE_SUPABASE_URL=https://xxx.supabase.co
VITE_SUPABASE_ANON_KEY=eyJ...
VITE_APP_ENV=production | development
```

仅这三个，且全部可公开（anon key 的安全性由 RLS 保证）。`service_role` key 不出现在任何前端环境。

### 12.2 环境划分

| 环境 | 前端 | 数据库 |
| --- | --- | --- |
| 本地 | `vite dev` | 默认连线上 Supabase（免费档只有一个项目）；单测用 Mock adapter |
| 预览 | GitHub Pages（PR 部署 / 同仓库分支） | 同上 |
| 生产 | GitHub Pages `gh-pages` 分支 | 同上 |

⚠️ 只有一个 Supabase 项目，**本地开发会写到生产数据**。缓解措施：本地默认启用 `VITE_APP_ENV=development`，此时应用只允许操作标题以 `[DEV]` 开头的行程；破坏性脚本（如 import-to-supabase）要求显式加 `--yes-i-mean-production`。这比申请第二个项目更省事，且够用。

### 12.3 CI/CD

```yaml
# .github/workflows/ci.yml（要点）
jobs:
  check:
    steps:
      - typecheck:  tsc --noEmit
      - lint:       eslint .
      - content:    tsx scripts/validate-content.ts     # 内容门禁
      - test:       vitest run --coverage
      - build:      tsx scripts/build-index.ts && vite build
```

部署：GitHub Pages 通过 `.github/workflows/deploy.yml`（本方案已附）在 `main` 推送时自动构建并发布到 `gh-pages` 分支；构建命令 `npm run build`，输出 `dist`，Vite `base: './'` 走相对路径。
SPA 路由用 **HashRouter**（见 3.2），无需 `404.html` 回退；CSP 已在 `index.html` 以 `<meta>` 声明。如需干净 URL，改 `createBrowserRouter` 并在发布时复制 `index.html` → `404.html` 即可。

数据库迁移：`supabase/migrations/*.sql` 手动在 SQL Editor 执行或用 `supabase db push`（本地 CLI）。个人项目不做迁移自动化，但**所有 DDL 必须进仓库**，这是重建数据库的唯一依据。

### 12.4 Supabase 免费档运维

- 闲置约 7 天自动暂停 → 加一个 GitHub Actions 定时任务（每 3 天）调一次只读 RPC 保活，零成本。
- 500MB 数据库对本项目（数千行记录）绰绰有余。
- **每周自动备份**：Actions 定时把关键表导出为 JSON 提交到私有分支（免费档无自动备份）。这条比保活更重要。

## 13. 测试策略

按"错了会不会砸招牌"分级投入：

| 层级 | 范围 | 工具 | 要求 |
| --- | --- | --- | --- |
| **L1 领域纯函数** | settle / split / closure-check / date-remap / sanity-check / privacy-filter / decideVisaCountry / staleness / rank | Vitest | **覆盖率 100%，含边界与属性测试** |
| L2 数据层 | Repository adapter 契约测试（同一组用例跑 Mock 与 Supabase 两个实现） | Vitest | 关键路径 |
| L3 权限 | RLS 越权断言：用户 B 尝试读/写用户 A 的行程、匿名尝试列 shares 表 | Vitest + 两个测试账号 | **每条策略至少一条否定用例** |
| L4 组件 | 关键交互（拖拽落位、投票、记账表单） | Testing Library | 少量 |
| L5 E2E | 建房 → 加 POI → 投票 → 出行程单 → 发布分享 → 无脑跟随 | Playwright | 1 条主流程，可选 |

**属性测试特别说明**：`settle` 用随机金额组合验证不变式 —— ① 转账后所有人净额为 0；② 转账笔数 ≤ n−1；③ 总额守恒。这类不变式测试比逐例断言更能发现问题。

**L3 必须写**：RLS 是本项目唯一的安全边界，而它写在数据库里、不会被 TypeScript 检查。一条漏写的策略等于全量数据裸奔。

## 14. 性能、可访问性与容错

**性能预算**

| 指标 | 目标 |
| --- | --- |
| 移动端首屏 JS（gzip） | < 120KB |
| PC 工作台首屏 JS（gzip） | < 220KB（Leaflet/dnd-kit 懒加载） |
| 首屏 LCP（4G） | < 2.0s |
| 行程页交互延迟（拖拽落位） | < 16ms（乐观更新，不等网络） |

手段：路由级 code splitting、Leaflet/记录编辑器/PDF 打印样式懒加载、世界库 JSON 走 SW 缓存、长列表（POI > 100）用简单虚拟滚动。

**可访问性**：语义化标签 + 焦点可见 + 拖拽键盘可达 + 对比度 ≥ 4.5:1。不追求 WCAG AA 全量达标，但键盘可达是刚需（对应"键盘友好"）。

**容错与降级**

| 故障 | 表现 |
| --- | --- |
| Supabase 不可达 | 自动切离线只读（有快照）/ 显示重试页（无快照），世界库浏览完全不受影响 |
| 世界库 POI 被删而行程仍引用 | 渲染"内容已下架"占位卡，保留时段与笔记，不崩 |
| POI JSON 结构不合预期（手改出错） | zod `safeParse` 失败 → 只渲染已知字段 + 控制台告警，不白屏 |
| 地图瓦片加载失败 | 显示灰底 + POI 列表 + "在地图 App 打开" |
| 打印样式异常 | 提供 Markdown / HTML 两种备用导出 |

全局 ErrorBoundary 按路由分段包裹，右栏详情面板崩溃不影响中栏时间线。
